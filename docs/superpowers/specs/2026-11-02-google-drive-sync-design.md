# Google Drive sync design

Approved intent: use the user's personal Google Drive (2 TB) to synchronize documents, folders, notes, chats, settings and learning progress across desktop and Android, anywhere, including offline edits. User requested setup guidance when ready. Credentials and device-specific sign-ins remain local.

## Architecture and decisions
- Keep the existing local filesystem as the offline source of truth; no runtime dependence on another device.
- Store immutable, versioned revisions in Google's private appDataFolder with drive.appdata, openid and email consent. No access to unrelated Drive files.
- Logical units: each chat, each terminal job, each document record, the complete graph family (including folders, as one consistency group), settings, browser preferences, and each prompt override. Independent preferences stay separate so a new device's sidebar setting cannot displace cloud model settings. Unknown files, live jobs, model caches, debug dumps, auth, env and sync bookkeeping are excluded. Original document and converted-text blobs are immutable, content-addressed objects, transferred one at a time before publishing their referencing metadata.
- A local baseline plus revision parent DAG detects concurrent edits and deletion conflicts without trusting device clocks. Tombstones prevent stale devices resurrecting deletions. Pick a deterministic head as the active version; retain losing versions locally and in immutable remote history and provide export controls. Do not merge graph ledgers independently.
- Capture local units synchronously; after network waits recheck fingerprints and activity before applying. Never apply incoming changes while model turns, jobs or extraction are active. Write files atomically and maintain recovery metadata. Single-flight sync; failures leave local content usable and retryable.
- Retain original uploads as content-addressed documents with logical-name metadata, including PDFs, so documents themselves follow the user. Existing imports cannot recover discarded original bytes.
- A minimal independently deployed HTTPS Google OAuth relay handles Google's web-client callback for desktop and Huawei alike. Devices poll with a secret PKCE verifier, so no fragile platform redirect or Google Play Services dependency. The relay stores only short-lived authorization codes; tokens are returned only after verifier validation. Refresh credentials remain on the device. Google client secret stays in relay secrets, never in the APK.
- Sync settings offers connect, sync now, disconnect, status, recoverable conflict export and one-time relay configuration. Mount a small background coordinator with the app. Incoming data triggers the existing UI notifications plus an explicit refresh notice for settings and open records.
- Disconnect removes only this device's credentials; revoking the whole Google grant is a separate explicit account action. Requests bind both account identity and connection generation across token-refresh waits.
- Default reconciliation is every 30 seconds while the local app server is running; UI checks status every 15 seconds while visible. File names and byte hashes, not timestamps, determine revisions. Independent chats and documents combine automatically; concurrent changes to one logical record preserve both versions.
- No cloud resources are created, deployed or billed without the user's one-time provider setup. Build/test changes locally first and then guide setup. No production uploads without the user's explicit Google consent.

## Acceptance
Two independent temp data roots converge through an in-memory Drive substitute; offline edits persist; unchanged sync is idempotent; concurrent edits and deletion conflicts retain both; remote paths cannot escape the data root; unknown/secret files never upload; interrupted or corrupt downloads cannot replace valid local files; account switching cannot upload another account's local data silently. Real Google login and three-device tests require the user's Cloud project.
